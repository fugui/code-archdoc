## 1. 系统愿景与产品定位 (Vision & Positioning)

### 1.1 项目愿景
`code-bench` 中纳管了大量存量业务代码仓，现有设计文档普遍存在**缺失、过时、流于表面或与代码实现不一致**的问题。**`code-archdoc`（代码设计文档反推与活体知识工作台）** 是挂载于 CodeBench 的平级微前端业务子系统，旨在建立**「代码为唯一事实源（Code as SSOT）+ 可插拔文档类型引擎 + 架构/研发双视角深度反推 + 人机双轨协同精修 + 双维漂移监控」**的工程化文档治理闭环。

### 1.2 核心价值主张
1. **先抽取事实、再生成文档（Extract Once, Render Many）**：先通过多语言静态分析抽取工程硬事实（Code IR）并自动降噪脱敏，再按需渲染多种文档类型，杜绝大模型编造接口、表名、配置键或泄漏明文凭据。
2. **可管理文档类型引擎（对标 `code-shield/tasks`）**：文档类型（`DocType`）是可插拔、目录约定 + Web 在线可管的一等公民；新增文档类型（含 AI 上下文包、Gap 诊断）优先以 `DocType` 形式扩展，而非在引擎中增加特例分支。
3. **架构深度与研发实战并重**：显式覆盖架构师关注的**运行时并发/资源模型、容错故障边界、关键约束/ADR**，以及开发者高频依赖的**端到端请求链路、本地构建排障与二次开发修改指南**。
4. **人机双轨精修与可度量质量**：工作台支持**手工直编 + Chat 局部精修**、Diff 审阅、源码证据直跳与章节锁定；以标准样例与「草稿→定稿修改量」等指标量化生成质量，而非凭主观感受。
5. **章节级双维保鲜**：基于证据锚点把「代码变更（Code Drift）+ 模板规范升级（Spec Drift）」定位到**具体章节**，防止文档再次腐烂。

## 6. 非目标边界界定 (Non-Goals)

- **Non-Goal 1（主数据自治禁令）**：不自建用户中心、部门树或代码仓主表，统一复用共享库 `users`、`departments`、`repositories` 与 `architecture_elements`。
- **Non-Goal 2（P0 语言与非纯文本格式边界）**：P0 不承诺 Go、TypeScript/React、Rust 等语言的高精度抽取，此类文件只做目录与基础文本摘要；C/C++ 不承诺宏展开与条件编译求值；**后端不执行 `.doc`/`.docx` 二进制黑盒解析，参考文档输入严格遵循前置转换后的纯 UTF-8 Markdown 契约（`ADR-10`）**。
- **Non-Goal 3（P0 Git 凭据与写操作边界）**：P0 不建设凭据保险库，不向远程仓库推分支/提 MR，不接入 Webhook（以 `F-25` 轮询替代）。
- **Non-Goal 4（P0 跨仓与多分支并存边界）**：P0 不做跨多个独立仓库的联合生成，且同一仓库同一时刻仅跟踪 1 条活跃目标分支（支持通过 `F-34` 切换跟踪分支，数据模型预留 `ref_name` 供 P1 `F-20` 支持多分支并存基线）；**一期参考文档版本变更或绑定调整不联动双维漂移雷达（`F-12`），仅在下次生成/刷新/Chat 时生效**。
- **Non-Goal 5（AI 驱动与受控只读隔离边界）**：P0 基线已通过 Go OpenAI Compatible HTTP/SSE 客户端（Native 引擎）完成闭环；自 `ADR-08` (`M14`) 起可选接入受进程级只读隔离的 OpenCode CLI 作为深度反推引擎，但仍严禁赋予任何 Agent 修改工作区源码、执行 Shell 命令、发起外网请求或越界访问父目录（OpenCode v2 仅对平级脱敏只读临时目录 `<canonicalRefDir>/*` 精确放行 `external_directory`，且严禁暴露含密钥的 `RootDir`）的权限，且不将外部 CLI 作为系统强制前置依赖（未安装或禁用时自动回退 Native）。
- **Non-Goal 6（表前缀与 UI 技术栈红线）**：不创建无 `archdoc_` 前缀的裸表；前端不引入 Ant Design / Material UI 等重型组件库，全面使用 `@code/common` 与原生 Vanilla CSS。
- **Non-Goal 7（`DocType` 零任意脚本红线）**：`DocType` 的范围裁剪、槽位结构与校验策略全部采用**声明式配置**，严禁引入可执行脚本。
- **Non-Goal 8（跨模块协同改造边界）**：对 `code-bench` 与 `code-common` 的协同改造严格限定在 §3 `D-01`~`D-04` 所列的通用能力范围内，不在宿主门户或公共库中混入 `archdoc` 专有业务逻辑。
- **Non-Goal 9（参考文档精修工作台一期轻量边界，`ADR-11`）**：一期不做「以码校文」（不拉取下属模块已发布反推文档或 L1 Code IR 进行跨仓一致性校验）、零新增参考文档对话/批注持久化表（采用无状态提案 + 前端内存审阅）、不引入反推 `DocType` 槽位契约（`slot_id`/`ownership`/`OrphanSection`）与审批发布状态机。

## 7. 非功能性与安全红线 (NFR & Guardrails)

1. **架构防腐与复用**：Code IR 解析器、`DocType` 注册表、参考文档领域引擎（`pkg/refdoc/`）、LLM 客户端、OpenCode 调度引擎（`pkg/opencode/`）与 Verifier 不得直接依赖数据库全局对象（严禁导入 `models`/`gorm`/`gin`），须通过领域接口解耦（具体检查机制见阶段二设计）；Git 沙箱能力复用 `D-04` 公共包，严禁复制粘贴。
2. **数据库隔离与测试红线**：所有 PG 读写单测使用 `testdb.SetupIsolatedDB(t)`；Git 同步、`DocType` 落盘、参考文档分层切片与分级凭据校验、Code IR 解析与脱敏、LLM 客户端（`httptest` Mock）、OpenCode 运行器（Fake CLI 脚本离线模拟）与 Verifier 均须覆盖正常、边界、异常与越权路径。
3. **沙箱、临时凭据与进程安全**：所有文件访问限定在 `(repo_id, subdir)` 沙箱根目录或经 `SafeJoin` 校验的 `ref_docs/` 目录内；`DocType` 目录名白名单校验，写盘须防并发损坏；`git` 与 `opencode` 子进程在取消/超时后必须通过进程组 `SIGKILL` 彻底回收；OpenCode 模式 A 生成的临时配置目录与含密钥配置文件严格限定 `0700`/`0600` 权限并在退出时立即销毁，绝不进入 `argv`、环境变量或日志；OpenCode v2 挂载的参考文档副本必须置于与 `RootDir` 平级的独立 `RefDir` 中并仅精确放行 `<canonicalRefDir>/*`。
4. **凭据防泄漏与双引擎安全权衡**：`APIKey` 加密存储、接口脱敏、日志与审计不打印明文；参考文档入库实施分级凭据门禁（硬阻断私钥/Token/URL 凭据与 `>4 KB` Base64 大图，疑似高熵支持显式确认脱敏，且支持管理员 `purge` 物理彻底擦除），并在工具读取与 OpenCode 副本写入前二次执行 `SecretRedactor`；Native 引擎对入参源码与工具输出强制执行 `SecretRedactor` 三级脱敏，而 OpenCode 引擎通过受限只读工具直接读取本地沙箱文件（不经过入参 `SecretRedactor`）；为此系统通过「只读沙箱权限隔离 + 管理员开关 + 前端显式提示 + 不可绕过的输出侧 Gate 4 Verifier 凭据硬阻断（`422 VERIFIER_BLOCKED`）」构成纵深防御，确保高敏仓库可显式选择 Native 或关闭 OpenCode，且任何引擎产出均无法将明文凭据写入已发布文档。
5. **提示词注入防护**：仓库内容（代码注释、旧文档、README）与用户上传的架构参考文档（`arch_reference_docs` / 摘录 / 工具输出）一律视为不可信被动数据，Native 路径以 128-bit 随机 `nonce` 数据栅栏包裹，OpenCode 路径以系统只读规约约束隔离；Chat 工具仅限沙箱与只读参考文档操作；凭据防泄漏校验与符号/引用门禁不依赖 LLM 自身判断。
6. **可观测与成本控制**：按 `F-27` 记录 Token、耗时、模型与阶段；保持稳定的上下文前缀顺序（含参考文档 L0 前缀），以提高推理服务的 Prompt KV Cache 命中率。
7. **前端体验与双模规范**：严格遵循工作区 `AGENTS.md`：`--color-*` Design Tokens 双主题、Flat BEM（`.code-archdoc-*`）、URL 同步 5 页滑动分页（默认 25 条/页）、禁止滥用 `any` 与静态内联 `style`。

## 8. 术语表 (Glossary)

| 术语 | 定义 |
| :--- | :--- |
| **Code IR (L1 静态事实层)** | 由确定性语法树/文本规则从代码仓直接提取、并完成降噪脱敏的结构化事实 JSON（目录树、数据模型、接口签名、运行时原语、配置键与依赖边界），每条事实带 `confidence`，是防幻觉的客观底座。 |
| **DocType (可管理文档类型)** | 对标 `code-shield/tasks` 的原子文档资产单元。服务端 `doc_types/<slug>/` 目录为唯一事实源，包含元数据、模板与生成/精修指令，支持 Web 在线全生命周期管理。 |
| **DocTypeRevision (文档类型修订快照)** | `DocType` 任一资产变更时生成的不可变聚合哈希快照，用于追溯文档的生成依据并驱动规范漂移检测。 |
| **DocPack (文档套件)** | 将多个启用中的 `DocType` 组合而成的标准交付方案（P1）。 |
| **Slot / `slot_id` (模板槽位)** | 模板中的结构化章节定义，声明数据来源、所有权模式（`auto`/`hybrid`/`locked`）与必填性；`slot_id` 跨模板修订保持稳定，是锁定、漂移定位与模板升级映射的关键。 |
| **交付波次 (`W1` / `W2`)** | P0 内部的交付顺序：`W1` 为最小可用纵向闭环，`W2` 补齐 P0 其余能力。 |
| **Golden Sample (标准样例)** | 由资深架构师针对代表性仓库人工撰写的标准文档，作为模板定稿依据与生成质量回归评测集。 |
| **Gap Report (过时与缺失差异报告)** | 以 `legacy-gap-report` `DocType` 实现，将代码事实与既有历史文档比对后输出的诊断清单（P1）。 |
| **Canvas Studio (双栏协同审校台)** | 集成文档树、手工直编与 Chat 精修、Diff 应用、章节锁定、图表缩放与源码证据直跳的交互式工作台。 |
| **Code Drift / Spec Drift (双维漂移)** | **Code Drift**：远端 `HEAD` 相对于已发布文档 `commit_sha` 的代码变更，按证据锚点定位到章节；**Spec Drift**：已发布文档所绑定的 `DocTypeRevision` 相对于最新模板修订的滞后，按 `slot_id` 定位到槽位。 |
| **Code IR Diff (语义级架构变更对比)** | 基于两次快照的确定性 Code IR 结构化比对，识别新增/变更/废弃的接口、数据模型、配置键与外部依赖（P1）。 |
| **ReferenceDoc / `OwnerScopeKey` (架构参考文档与归属作用域)** | 用户按架构树层级（`system` / `subsystem` / `group` / `repo` / `module`）上传并维护的纯 UTF-8 Markdown 设计上下文资产；`OwnerScopeKey` 对应 `is_home=true` 的唯一归属作用域，独占控制正文编辑、版本升级与归档权限，跨节点消费绑定仅控制本节点引用与继承策略（`ADR-10`）。 |
| **RefDocCitation (`RefCitationsJSON`)** | 独立存储在 `SectionEvidence.RefCitationsJSON` 与 `ChatProposalItem.RefCitationsJSON` 中的参考文档章节溯源条目（`ref_doc:<id>@v<ver>#<sec>`），与源码/模块证据 `EvidencesJSON` 物理隔离，支持历史已解绑引用的 `stale` 无损兼容展示（`ADR-10`）。 |
| **RefDoc Studio / 不可变前滚恢复 (参考文档精修工作台)** | 挂载于 `/ref-docs/:docId/studio` 的轻量三栏工作台，支持按 `TOC` 自由分节编辑、无状态 AI 精修提案（经 `ValidateAndParse` + `RunMermaidGate` 预检并豁免 `RunSymbolGate`）及基于磁盘 `v1..vN.md` 的 Diff 比对；「恢复旧版 `vK`」严格经当前 `expected_version` 发布为 `v<N+1>.md`，确保历史快照不可变（`ADR-11`）。 |
